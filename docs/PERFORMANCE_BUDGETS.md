# Performance budgets (LOOM-698)

Proposed targets — measure with `npm run build` transfer sizes, Vitest perf helpers, and manual Lighthouse on `out/` + local Worker. Not current production SLAs.

| Journey step | Target (desktop) | Target (phone) | Owner module |
|--------------|------------------|----------------|--------------|
| Cold load (static `/`) | First Load JS ≤ 600 kB (Next report) | Same bundle; TTI ≤ 4 s on throttled 4G | `next build`, code-splitting |
| Discover scan (desktop) | ≤ 8 s for full feed scan | ≤ 3 s for 120-card cap | `discoverStories.ts` |
| Browser CSV parse | ≤ 2 s for 50k cells | ≤ 1 s for 500-row sample cap | `mock-data.ts`, `webIngest.ts` |
| Chart interaction | 60 fps pan/zoom on ≤ 50k scatter points (Canvas/WebGPU) | 30 fps acceptable on dense scatter | `ChartView`, `webgpu.ts` |
| Worker source poll | p95 ≤ 5 s upstream + parse | Same | `catalog-proxy.ts` |
| IndexedDB import | No full-table `getAll` on eviction | Same | `webFileStore.ts` |

**Representative inputs:** `.loom-data` 10k-row scatter sample; live `stream://usgs` buffer; 500-row web upload.

**Regression gates:** `make ci` (tsc, Vitest, build); optional `npm run bundle-budget` when changing imports.

**Recording baselines:** Note device, build id, and `npm run build` First Load JS in PR when changing budgets.

**Chart editor refinement (2026-10-14):** History is bounded to 20 snapshots in each direction and contains no dataset rows. Rapid numeric adjustments reuse a checkpoint (600 ms window), avoiding a deep snapshot on each slider tick. Named looks are capped at 20 and write to storage only when the library reference changes. Collapsed visual sections mount on demand. These changes stay outside parsing and canvas draw loops; check the Next First Load JS report against the 600 kB target when building.

Local macOS production build `2026-10-15T00:07:39.168Z` reported **366 kB First Load JS** for `/` (previous pass: 365 kB), within the proposed 600 kB budget. This is a bundle-size comparison, not a frame-rate or mobile timing measurement.

**Discovery landing refinement (2026-10-15):** The gallery initially mounts 24 previews, adds 24 within 240 px of the scroll area's bottom (or through the fallback button), and retains the existing 120-story mobile cap. Offscreen previews defer drawing. Flow, Tiles, and List use CSS layout; Masonry observes natural card heights without rebalancing earlier stories on append. Only the first page uses diversity interleaving (at most 24 passes over candidates). Full source snapshots (up to `SOURCE_EXPLORE_ROWS`) are shared between variants rather than copied, aligning headlines with the opened data. Aggregate thumbnails use all snapshot rows; dense point previews retain a 1,500-point cap. Their row cache uses weak snapshot keys so an expired scan can be collected. This trades a larger per-feed probe for fewer mounted canvases and accurate aggregation; the scan timing targets above still require device measurements.

Daily picks persist in IndexedDB with one snapshot per feed. Warm opens skip scanning and recommendation generation; chart activation uses prepared alternatives and starts reconnecting only after activation. Stale refreshes preserve the existing gallery. Background scans use six concurrent probes on desktop / three on mobile, yield between feeds, and batch progressive updates (150 ms after the first batch). This favors interaction responsiveness over the old all-at-once cold-scan target; the full cold sweep can take longer than eight seconds when upstreams time out. Returning/shared charts get five seconds before background warming begins. These are scheduling changes, not measured FPS or latency guarantees.

Further discovery upkeep uses the source registry's cadence (minimum one minute, one day for load-once feeds), refreshes at most six due feeds per check (half reserved for the oldest catalog feeds, the rest prioritizing visible feeds), and backs off failed checks for five minutes. Partial scans merge only newer captures and retain the mobile cap. Related recipes share one card/canvas instead of mounting duplicate perspectives, while the exact selected recommendation remains intact. Refresh results wait behind an update control while browsing. Scroll writes stay in refs; session storage holds only bounded browse preferences. The return button lazy-loads the discovery module rather than expanding the initial navigation bundle.

Canvas Arrange mode previews pointer changes at most once per animation frame and commits history only on release. It adds no dataset copies. Ordinary charts keep their existing renderer outside Arrange mode.

**Typography refinement (2026-10-16):** Font resolution and contrast correction run on small text/legend sets, outside row parsing and aggregation. Font downloads are opt-in and deduplicated per selected family; device mode adds no font requests. Font completion triggers a canvas repaint so measured labels use the loaded face. Larger text uses the existing density limits and label thinning; this adds no dataset copies. Font-stack lookup is constant-time. Shared text fitting has an allocation-free ASCII segmentation path and a bounded cache of 128 Unicode labels (at most 512 UTF-16 units each); measured widths are never reused across fonts. Readout geometry observes only the tooltip element, and remeasures wrapped content or viewport/font changes. Cube fitting projects eight corners, independently of dataset size; collision checks operate only on the thinned axis labels. Check the production bundle below against the same 600 kB budget; visual checks are not frame-rate measurements.

**Broader discovery consideration (2026-10-16):** Candidate generation visits the complete chart catalog and all source measures/pairs before qualification and the 160-recipe per-feed retention limit. Mobile considers the same pool before selecting its 120-story cache. Snapshot rows remain shared. Window slices, numeric profiles and analysis results are reused across presentation variants. Probe qualification yields every 24 candidates, allowing input and paints between batches. The gallery groups analytical questions before ranking, then applies diversity to every page; only 24 previews mount initially. Per-page ranking examines a 96-item lookahead plus the best remaining representative of every source, chart kind and family, rather than rescanning the entire gallery for each pick. More candidates increase scan CPU and recipe cache size; cold-sweep/device timing targets still need measurement. Quality checks exclude thin histories, flat/null measures, invalid transforms and invented geographic paths before previews mount.

**Expressive discovery and rolling upkeep (2026-10-16):** Source-aware emoji and category-shape variants reuse existing snapshots and renderers. Emoji candidates are rejected above 1,200 points per panel, matching native renderer limits; dense geometric previews retain their existing cap. Check-time-independent snapshot fingerprints are computed once per immutable snapshot with weak memoization. Quiet polls retain chart/sample references. Upkeep scans bounded batches across all sources while the app/tab is active, including missing sources, and backs off failures. Browsing stages real updates; closed apps do not poll. These changes add candidate qualification and content hashing work; device scan timing remains to be measured.
